// 00the problem

Two agents. One wall.

You're running two harnessed agents — Claude Code on your laptop, Claude Code on a teammate's, maybe one in a VM. Each has its context, its files, its memory. There is no way for them to talk to each other, let alone hand off a file or ask a question without going through the cloud.

The internet is the wrong layer for this. The LAN is right there.

// 01topology

One node per harness.

Each harness instance spawns a local agentmesh process. The harness talks to its own node over stdio MCP. The nodes do the P2P — mDNS to discover each other, mTLS to talk.

// 02install

One line. Then it's just there.

The installer downloads the latest signed release, verifies its sha256, drops the binary in place, and asks which harness(es) to register with — Claude Code, Cursor, ChatGPT Codex, Antigravity, or all four. Open the harness afterwards and the eight mesh_* tools are already wired up.

linux / macOS 
$ curl -fsSL https://blueheisenberg.github.io/agentmesh/install.sh | sh
windows · powershell 
PS> iwr -useb https://blueheisenberg.github.io/agentmesh/install.ps1 | iex
  Where should I register agentmesh?
    1) claude code     ~/.claude.json
    2) cursor          ~/.cursor/mcp.json
    3) chatgpt codex   ~/.codex/config.toml
    4) antigravity     ~/.gemini/antigravity/mcp_config.json
    5) all of the above
    6) none — I'll do it manually
  choose (comma-separated, e.g. 1,2) [default: 1]: _

Non-interactive? Pass env vars to sh / set $env: before iex: HARNESS=claude,cursor, VERSION=v0.2.0, NAME=davids-laptop, SKIP_REGISTER=1. Idempotent — safe to re-run; a .bak of every config is written before any edit.

Then add to your harness's MCP config. For Claude Code, ~/.claude.json:

~/.claude.json 
{
  "mcpServers": {
    "agentmesh": {
      "command": "/abs/path/to/agentmesh",
      "args": ["serve", "--name=your-laptop"]
    }
  }
}

Restart the harness. The agent now has eight mesh_* tools.

// 03how it works

Four jobs, same code on every node.

  1. identity

    An Ed25519 keypair, persisted to ~/.agentmesh/identity.json. The public key, hex-encoded, is your peer_id. The same keypair becomes a self-signed X.509 certificate used by TLS — no CA, no renewal.

  2. discovery

    Advertise _agentmesh._tcp.local over mDNS with the peer_id in the TXT record. Browse for the same service type. Peers come and go automatically; nothing to configure.

  3. transport

    HTTPS on a random LAN port. Every connection is mTLS 1.3. The client pins the server's cert against the peer_id it expected from mDNS. A LAN attacker can advertise an arbitrary peer_id — they can't talk to you as that peer without the private key.

  4. mcp shim

    Each tool is a thin wrapper over the node — mesh_send POSTs to a peer's /v1/msg; mesh_fetch GETs /v1/share/{handle}. The harness never speaks mDNS or TLS; it just speaks MCP.

What changes.

without agentmesh with agentmesh

// 05mcp tools

Eight tools. That's all.

All take JSON arguments, return JSON. The agent decides when to use them.

mesh_whoami
peer_id, name, port, version.
mesh_peers
list peers discovered on the LAN.
mesh_send
send a JSON message to a peer, or "*" to broadcast.
mesh_inbox
read incoming messages. wait_seconds long-polls.
mesh_share
register a file as shareable. Returns a handle.
mesh_fetch
fetch a shared blob from a peer. Inline or to disk.
mesh_shares
list local shares currently on offer.
mesh_unshare
revoke a share by handle.

// 06trust model

Encrypted by construction.

The threat model is a trusted LAN. Within that perimeter, four things are true.

  • All traffic is mTLS 1.3, Ed25519-backed self-signed certs. The encryption isn't optional, can't be downgraded, and the cert pinning happens against the peer_id from mDNS.
  • Identity is the public key. The peer_id is the hex of the Ed25519 pubkey. Every authenticated request's "from" is the validated cert pubkey — body-claimed identity fields are cross-checked.
  • Discovery is open. Anyone on the LAN advertising _agentmesh._tcp shows up in your peer table. Messages from unknown peers are flagged first_contact: true in the inbox — the agent decides.
  • Files require explicit share. Nothing on disk is reachable until the sender calls mesh_share. allow_peers restricts to specific peer_ids, and those restrictions can't be spoofed.

// 07not in the box

What this isn't.

  • No NAT traversal. This is a LAN tool. If you need agents across the open internet, you want a relay, not a mesh.
  • No persistence. The inbox lives in memory. If the node dies, the queue dies with it.
  • No file streaming primitives. A "file" is a single HTTPS GET. Want resumable transfer? Layer it on mesh_share + your own protocol.
